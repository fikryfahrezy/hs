# Technical Specification

> Status: Ready

## Purpose

Define the implementation-ready contracts for the Habit Shaper MVP. This
document specifies the exact MySQL model, shared transport schemas, REST
behavior, authentication mechanism, calendar algorithms, ownership rules,
idempotency guarantees, and transaction boundaries.

The [Product Implementation Plan](./07-implementation-plan.md) remains the
source of truth for product scope, user experience, delivery order, and
acceptance criteria. Repository-wide code, tooling, styling, CI, and testing
conventions remain in their existing documents.

## Status lifecycle

- **Draft**: implementation decisions may still change during review.
- **Ready**: all blocking decisions are resolved and implementation may begin.
- **Implemented**: the shipped code and migrations match this specification.
- **Superseded**: another document or recorded decision replaced this design.

Changes made after the document reaches Ready must update this specification in
the same commit as the affected contract or migration.

## Scope

This specification covers:

- users and email/password authentication;
- build and break habits;
- build-habit completion events;
- break-habit relapse events;
- derived streak and weekly progress values;
- goals linked to habits;
- user ownership and authorization;
- REST request, response, and error shapes; and
- migration and transactional behavior.

It does not define visual CSS values, component markup, CI YAML, Dockerfile
instructions, or test-runner configuration. Those concerns are owned by the
corresponding engineering documents.

## System boundary

The browser calls one same-origin REST API through Nginx:

```text
React application
      |
      | HTTPS/HTTP, JSON, HTTP-only authentication cookie
      v
Nginx /api proxy
      |
      v
NestJS REST controller
      |
      v
application use case -> domain calculation -> repository -> MySQL
```

The API is authoritative for authentication, ownership, the user's current
calendar date, event eligibility, and all calculated tracking values. The
frontend may format returned data but must not independently redefine streak or
weekly-stat rules.

## Shared conventions

### Identifiers

- Application entities use UUID version 4 identifiers generated by an injected
  application ID generator.
- UUIDs use canonical lowercase text with hyphens.
- MySQL stores entity UUIDs as their 128-bit value in `BINARY(16)` columns.
- Path identifiers that are not canonical UUIDs fail request validation before
  a repository call.

The API and application layers continue to use readable UUID strings. The API
repository boundary converts a validated string to a 16-byte `Buffer` before
binding it to indexed predicates. Select projections convert stored UUIDs with
`LOWER(BIN_TO_UUID(column)) AS id`, so repositories can return compatible typed
rows directly. This keeps database keys and indexes compact without leaking
binary identifiers into application, transport, logging, or frontend code.

Repository conversion uses the UUID's 32 hexadecimal digits in network order;
it does not reorder UUID fields. MySQL's version-1 time-part swap mode is not
used because application IDs are UUID version 4.

### Transport and application names

- JSON request and response properties use `snake_case`.
- URL query parameters and documented route parameter names use `snake_case`.
- Database columns use `snake_case`.
- Internal code may reuse compatible `snake_case` database or contract shapes
  directly. Use `camelCase` for domain-specific values where no external shape
  is being reused; do not add casing-only mappers.
- REST controllers parse requests and delegate to use cases. Application
  services construct response-ready class DTOs when serialization is required,
  and controllers return those DTOs without another mapper.
- Frontend API adapters parse snake-case response contracts and map them to
  camel-case feature values before returning data to hooks or components.
- ISO calendar dates use `YYYY-MM-DD` strings.
- Timestamps use UTC ISO 8601 strings with a `Z` suffix.
- Optional stored values are returned as `null`, not omitted, when the response
  schema declares them nullable.

### Database defaults

- Use a pinned MySQL 8 release that enforces declared checks and foreign keys.
- Use the InnoDB storage engine.
- Use `utf8mb4` with `utf8mb4_0900_ai_ci` as the table default unless a column
  explicitly declares an ASCII identifier or binary UUID value.
- Configure every application and migration connection for UTC.
- Configure the `mysql2` pool with `timezone: "Z"`.
- Use `DATETIME(3)` for audit timestamps and `DATE` for user calendar dates.
- Keep strict SQL mode enabled.
- Do not use soft deletion in the MVP.

### API defaults

- The API prefix is `/api`.
- Request and response bodies use `application/json; charset=utf-8`.
- Successful resource responses return the resource directly rather than a
  generic `data` envelope.
- Successful deletion and logout operations return `204 No Content` with no
  response body.
- Unknown JSON properties are rejected by strict request schemas.
- Lists are unpaginated in the MVP and use deterministic ordering.

## Relational model

```text
users 1 ──────< habits 1 ──────< habit_completions
                       |
                       ├────────< habit_relapses
                       |
                       └────────< goals
```

Habit ownership comes from `habits.user_id`. Completion, relapse, and goal
ownership is inherited through their required habit relationship. Child tables
do not duplicate `user_id`; every owned child query joins or scopes through the
parent habit.

Deleting a user cascades to habits. Deleting a habit cascades to completions,
relapses, and goals. The application does not expose user deletion in the MVP,
but the relational model remains internally consistent.

## MySQL schema

The definitions below are normative. Migration names may contain generated
timestamps, but the table and constraint behavior must match this section.

### `users`

| Column          | MySQL definition                                                                   | Notes                                   |
| --------------- | ---------------------------------------------------------------------------------- | --------------------------------------- |
| `id`            | `BINARY(16) NOT NULL`                                                              | UUID v4 primary key stored as 128 bits. |
| `email`         | `VARCHAR(254) NOT NULL`                                                            | Trimmed and lowercased before storage.  |
| `password_hash` | `VARCHAR(255) NOT NULL`                                                            | Encoded Argon2id hash only.             |
| `timezone`      | `VARCHAR(64) NOT NULL`                                                             | IANA name validated by the application. |
| `created_at`    | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`                                | UTC.                                    |
| `updated_at`    | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)` | UTC.                                    |

Constraints and indexes:

```sql
PRIMARY KEY (id)
UNIQUE KEY users_email_unique (email)
```

The normalized email is the display and login value in the MVP; a second raw
email column is unnecessary. The table collation makes the unique index
case-insensitive, while application normalization prevents representation
differences.

### `habits`

| Column       | MySQL definition                                                                   | Notes                                   |
| ------------ | ---------------------------------------------------------------------------------- | --------------------------------------- |
| `id`         | `BINARY(16) NOT NULL`                                                              | UUID v4 primary key stored as 128 bits. |
| `user_id`    | `BINARY(16) NOT NULL`                                                              | Owning user UUID.                       |
| `name`       | `VARCHAR(100) NOT NULL`                                                            | Trimmed, non-empty name.                |
| `type`       | `ENUM('build', 'break') NOT NULL`                                                  | Immutable after creation.               |
| `start_date` | `DATE NOT NULL`                                                                    | User-local date assigned by the server. |
| `created_at` | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`                                | UTC.                                    |
| `updated_at` | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)` | UTC.                                    |

Constraints and indexes:

```sql
PRIMARY KEY (id)
KEY habits_user_created_index (user_id, created_at, id)
CONSTRAINT habits_user_foreign
  FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
```

Names do not need to be unique. A user may intentionally create two habits with
the same display name. Habit type and start date are immutable in the MVP
because changing them would reinterpret existing event history.

### `habit_completions`

| Column            | MySQL definition                                    | Notes                     |
| ----------------- | --------------------------------------------------- | ------------------------- |
| `habit_id`        | `BINARY(16) NOT NULL`                               | Parent build-habit UUID.  |
| `completion_date` | `DATE NOT NULL`                                     | User-local completed day. |
| `created_at`      | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)` | UTC event creation time.  |

Constraints and indexes:

```sql
PRIMARY KEY (habit_id, completion_date)
CONSTRAINT habit_completions_habit_foreign
  FOREIGN KEY (habit_id) REFERENCES habits (id) ON DELETE CASCADE
```

The composite primary key is the idempotency constraint and the bounded-range
lookup index. A separate event UUID is unnecessary because the API addresses a
completion by habit and calendar date.

MySQL cannot express the cross-table rule that the parent habit must be a build
habit. The application verifies the owned habit type before inserting or
deleting a completion.

### `habit_relapses`

| Column         | MySQL definition                                    | Notes                    |
| -------------- | --------------------------------------------------- | ------------------------ |
| `habit_id`     | `BINARY(16) NOT NULL`                               | Parent break-habit UUID. |
| `relapse_date` | `DATE NOT NULL`                                     | User-local relapse day.  |
| `created_at`   | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)` | UTC event creation time. |

Constraints and indexes:

```sql
PRIMARY KEY (habit_id, relapse_date)
CONSTRAINT habit_relapses_habit_foreign
  FOREIGN KEY (habit_id) REFERENCES habits (id) ON DELETE CASCADE
```

The primary-key order also supports `MAX(relapse_date)` for one habit. The
application verifies that the owned parent is a break habit. The API records
today's relapse only, so it does not accept a client-controlled relapse date.

### `goals`

| Column        | MySQL definition                                                                   | Notes                                          |
| ------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------- |
| `id`          | `BINARY(16) NOT NULL`                                                              | UUID v4 primary key stored as 128 bits.        |
| `habit_id`    | `BINARY(16) NOT NULL`                                                              | Required linked-habit UUID and ownership path. |
| `title`       | `VARCHAR(120) NOT NULL`                                                            | Trimmed, non-empty title.                      |
| `description` | `VARCHAR(500) NULL`                                                                | Trimmed; blank input becomes `NULL`.           |
| `created_at`  | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`                                | UTC.                                           |
| `updated_at`  | `DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)` | UTC.                                           |

Constraints and indexes:

```sql
PRIMARY KEY (id)
KEY goals_habit_updated_index (habit_id, updated_at, id)
CONSTRAINT goals_habit_foreign
  FOREIGN KEY (habit_id) REFERENCES habits (id) ON DELETE CASCADE
```

A habit may own multiple goals. Goals do not carry numeric progress, deadlines,
or completion state in the MVP.

## Migration sequence

Create one forward migration with a Dbmate down section for each product slice:

1. create `users`;
2. create `habits`;
3. create `habit_completions`;
4. create `habit_relapses`; and
5. create `goals`.

Down sections drop only the table introduced by that migration. The natural
reverse order respects foreign keys. Do not edit an applied migration after it
has entered the main branch; add a new corrective migration.

The Compose `migrate` service applies every pending migration before the API
starts. Migrations contain schema only; no example user, password, or product
seed data is required for normal startup.

## Calendar model

### Resolving the user's date

The authoritative current date is derived from the injected clock instant and
the authenticated user's stored IANA timezone. The client never supplies
"today" for a business decision.

At registration:

1. trim the submitted timezone;
2. verify it using the Node.js ICU timezone implementation;
3. store the exact canonical or accepted IANA name; and
4. reject an invalid zone with a field validation error.

The frontend proposes `Intl.DateTimeFormat().resolvedOptions().timeZone` during
registration. There is no timezone-editing workflow in the MVP.

### Date-only arithmetic

- Parse ISO dates into validated year, month, and day components.
- Convert date-only components to an integer epoch-day value using UTC calendar
  arithmetic before subtracting dates.
- Never calculate calendar-day differences by subtracting local midnight
  timestamps; daylight-saving transitions can make that result non-integral.
- Derive Monday week boundaries from the validated date-only representation.
- Domain calculations receive ISO dates or a small calendar-date value object,
  not unrestricted JavaScript `Date` instances.

### Week selection

`GET /habits` accepts an optional `week_start` query value:

- omitted: use the Monday containing the user's current date;
- supplied: require a valid ISO date that is a Monday;
- allow the current or a previous week; and
- reject a future week with `VALIDATION_ERROR`.

The UI initially requests only the current week. Historical read support costs
little once the bounded queries and calculations exist and makes the contract
unambiguous without adding a historical navigation feature to the MVP.

## Tracking algorithms

### Weekly build day states

Return exactly seven entries, Monday through Sunday, for every build habit.
Assign one state to each date in this order:

1. `ineligible` when the date is before `habit.start_date`;
2. `future` when the date is after the user's current date;
3. `completed` when an eligible completion exists;
4. `pending` when the date is today and no completion exists; or
5. `missed` when the eligible date is before today and no completion exists.

Only `completed`, `pending`, and `missed` dates are eligible. A date is mutable
when it is eligible, belongs to the user's current week, and is not in the
future. Completed and missed dates from earlier weeks are read-only because the
MVP permits corrections only within the current week.

Weekly counts are derived from the seven states:

The calculation pseudocode uses the internal camel-case domain convention. Its
REST response fields use the snake-case names defined in the contract section.

```text
completedDayCount = number of completed states
missedDayCount = number of missed states
pendingDayCount = number of pending states
evaluatedDayCount = completedDayCount + missedDayCount

if evaluatedDayCount is 0:
  completionRatePercent = 0
else:
  completionRatePercent = round(
    completedDayCount / evaluatedDayCount * 100
  )
```

An incomplete today remains pending, so it does not reduce the weekly rate or
count as missed before the day has ended. Completing today adds it to both the
completed and evaluated counts.

Example for a habit started Monday when the user date is Wednesday:

```text
Monday complete, Tuesday missing, Wednesday pending, later days future

completedDayCount: 1
missedDayCount: 1
pendingDayCount: 1
completionRatePercent: 50
```

### Current build streak

Determine the streak anchor:

```text
if today has a completion:
  anchor = today
else:
  anchor = yesterday
```

Starting at the anchor, count consecutive completion dates backward until:

- an eligible date has no completion;
- the candidate date falls before the habit start date; or
- there are no more completion records.

Today is allowed to remain pending without prematurely breaking yesterday's
streak. A new habit with no completions has a zero-day streak. Backfilling or
removing a completion in the current week immediately changes the derived
result; no streak counter is persisted.

Examples:

```text
Started Monday; Monday and Tuesday complete; Wednesday is today and pending
=> current streak 2

Started Monday; Monday and Wednesday complete; Wednesday is today
=> current streak 1

Started today; today pending
=> current streak 0
```

### Completion eligibility

`PUT` and `DELETE` completion operations require all of the following:

- the habit exists and belongs to the authenticated user;
- the habit type is `build`;
- the date is valid ISO format;
- the date is not before the habit start date;
- the date is not after the user's current date; and
- the date is within the Monday-to-Sunday current week.

An ineligible date produces `409 DATE_NOT_ELIGIBLE`. A break habit produces
`409 INVALID_HABIT_TYPE_OPERATION`.

### Current clean streak

For a break habit, retrieve the greatest relapse date that is not after today.
Then calculate:

```text
if latestRelapseDate is today:
  currentCleanStreak = 0
else if latestRelapseDate exists:
  currentCleanStreak = calendarDayDifference(latestRelapseDate, today)
else:
  currentCleanStreak = calendarDayDifference(startDate, today) + 1
```

Examples:

```text
Started today with no relapse       => day 1
Relapsed today                      => day 0
Relapsed yesterday                  => day 1
Relapsed three calendar days ago    => day 3
```

Recording a relapse is supported only for today. The composite primary key
makes a repeated same-day request idempotent. No clean-streak counter or daily
"clean" event is stored.

## Authentication specification

### Email normalization

Registration and login apply the same normalization:

1. trim surrounding whitespace;
2. lowercase using a locale-independent conversion; and
3. validate the normalized result as an email no longer than 254 characters.

Do not apply provider-specific transformations such as removing dots or plus
aliases.

### Password requirements and hashing

- Registration passwords contain between 8 and 128 Unicode characters.
- Passwords are not trimmed or otherwise normalized.
- Hash with Argon2id using the pinned `argon2` Node.js package.
- Configure a 16-byte random salt, 32-byte hash, 19,456 KiB memory cost, two
  iterations, and one lane as the initial development parameters.
- Keep the parameters encoded in the stored hash so they can be upgraded later.
- Compare hashes through the library's verification function.
- Never log password values, password hashes, authentication cookies, or JWTs.

The selected parameters were exercised with `argon2` 0.45.1 inside the final
Node.js 24.20.0 API container during scaffolding. Hash-and-verify completed in
66 ms on the development machine. If later deployment measurements require an
adjustment, record the changed values here rather than silently changing code
defaults.

### Signed token

Use one JWT access token with:

- algorithm: `HS256`;
- subject (`sub`): user UUID;
- issuer (`iss`): `habit-shaper-api`;
- audience (`aud`): `habit-shaper-web`;
- issued-at (`iat`): token issue time; and
- expiration (`exp`): seven days after issue.

`JWT_SECRET` is always required and must contain at least 32 bytes of
unpredictable value. Compose supplies a local-only default for one-command
development startup; production deployments must override it. Token verification
pins the expected algorithm, issuer, and audience.

### Cookie

| Attribute  | Value                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------ |
| Name       | `hs_session`                                                                                                       |
| `HttpOnly` | `true`                                                                                                             |
| `SameSite` | `Lax`                                                                                                              |
| `Path`     | `/`                                                                                                                |
| `Max-Age`  | Seven days, matching the token lifetime                                                                            |
| `Secure`   | Controlled by validated `COOKIE_SECURE`; `false` for documented local HTTP Compose and `true` for HTTPS deployment |

The frontend sends same-origin credentials through the centralized API client.
The token is never exposed to JavaScript or stored in local storage.

The production topology is same-origin and does not enable permissive CORS.
SameSite cookies, JSON-only mutation bodies, and the same-origin deployment are
the MVP cross-site request protections. If the API is later served cross-origin,
explicit origin and CSRF controls must be designed before changing cookie
settings.

### Authentication throttling

- Registration: five requests per 15 minutes per source IP.
- Login: ten requests per 15 minutes per source IP.
- Return `429 RATE_LIMITED` when a limit is exceeded.

The limits protect the public credential endpoints without adding CAPTCHA or an
account-lockout workflow to the MVP.

## REST contracts

### Common user representation

```ts
type UserResponse = {
  id: string;
  email: string;
  timezone: string;
  created_at: string;
};
```

`id` is a UUID, `timezone` is a valid IANA name, and `created_at` is a UTC ISO
timestamp.

### `POST /api/auth/register`

Request:

```ts
type RegisterRequest = {
  email: string; // normalized result: 1..254
  password: string; // 8..128 characters
  timezone: string; // valid IANA name, max 64
};
```

Example:

```json
{
  "email": "person@example.com",
  "password": "correct horse battery staple",
  "timezone": "Asia/Jakarta"
}
```

Success: `201 Created`, sets `hs_session`, returns `UserResponse`.

Failures:

- `400 VALIDATION_ERROR` for invalid fields;
- `409 EMAIL_ALREADY_EXISTS` for a normalized duplicate; and
- `429 RATE_LIMITED` when throttled.

The database unique index remains the final concurrency-safe duplicate check.

### `POST /api/auth/login`

Request:

```ts
type LoginRequest = {
  email: string;
  password: string;
};
```

Success: `200 OK`, sets `hs_session`, returns `UserResponse`.

Failure: `401 INVALID_CREDENTIALS` for an unknown email or incorrect password.
The body and observable status are identical for both cases.

### `POST /api/auth/logout`

Request body: none.

Success: `204 No Content`. Clear `hs_session` using the same path and cookie
attributes used when setting it. Logout is idempotent and succeeds when the
cookie is missing or invalid.

### `GET /api/auth/me`

Success: `200 OK` with `UserResponse`.

Failure: `401 AUTHENTICATION_REQUIRED` for a missing, expired, malformed, or
invalidly signed token, or when the subject user no longer exists.

### Habit representations

```ts
type HabitType = "build" | "break";

type HabitCommon = {
  id: string;
  name: string;
  type: HabitType;
  start_date: string;
  created_at: string;
  updated_at: string;
};

type BuildDayState = {
  date: string;
  state: "ineligible" | "future" | "completed" | "pending" | "missed";
  mutable: boolean;
};

type BuildHabitResponse = HabitCommon & {
  type: "build";
  tracking: {
    current_streak: number;
    week: {
      starts_on: string;
      ends_on: string;
      completed_day_count: number;
      missed_day_count: number;
      pending_day_count: number;
      completion_rate_percent: number;
      days: BuildDayState[]; // exactly seven, Monday first
    };
  };
};

type BreakHabitResponse = HabitCommon & {
  type: "break";
  tracking: {
    current_clean_streak: number;
    last_relapse_date: string | null;
  };
};

type HabitResponse = BuildHabitResponse | BreakHabitResponse;
```

All streak and count values are non-negative integers. The completion rate is
an integer from 0 through 100.

### `GET /api/habits`

Query:

```ts
type ListHabitsQuery = {
  week_start?: string; // ISO Monday; defaults to current user's week
};
```

Success: `200 OK` with `HabitResponse[]`, ordered by `created_at` ascending and
then `id` ascending so the daily layout remains stable.

The repository retrieves owned habits, build completions needed for the selected
week and current-streak lookback, and latest break relapses without issuing one
query per habit. The application layer assembles the discriminated response.

### `POST /api/habits`

Request:

```ts
type CreateHabitRequest = {
  name: string; // trimmed result: 1..100 characters
  type: "build" | "break";
};
```

Example:

```json
{
  "name": "Meditate",
  "type": "build"
}
```

Success: `201 Created` with the created `HabitResponse` for the current week.
The server assigns `start_date` using the authenticated user's current date.

### `DELETE /api/habits/:habit_id`

Success: `204 No Content`. Database cascades remove tracking events and goals.

Failure: `404 RESOURCE_NOT_FOUND` for an unknown or differently owned habit.
The response does not reveal cross-user existence.

### `PUT /api/habits/:habit_id/completions/:date`

Request body: none. The path date is an ISO calendar date.

Success: `200 OK` with the recalculated `BuildHabitResponse` for the user's
current week.

The operation is ensure-present semantics. Repeating it returns the same logical
result without creating a duplicate row.

Failures:

- `404 RESOURCE_NOT_FOUND` for an unknown or differently owned habit;
- `409 INVALID_HABIT_TYPE_OPERATION` for a break habit; and
- `409 DATE_NOT_ELIGIBLE` for a future, pre-start, or non-current-week date.

### `DELETE /api/habits/:habit_id/completions/:date`

Request body: none.

Success: `200 OK` with the recalculated `BuildHabitResponse` for the current
week. The operation is ensure-absent semantics; deleting an already absent
eligible completion still succeeds.

Failure behavior matches the completion `PUT` operation.

### `POST /api/habits/:habit_id/relapses`

Request body: none. The server supplies today's date from the user's timezone.

Success: `200 OK` with the recalculated `BreakHabitResponse`. Repeating the
request on the same local date returns the same logical result.

Failures:

- `404 RESOURCE_NOT_FOUND` for an unknown or differently owned habit; and
- `409 INVALID_HABIT_TYPE_OPERATION` for a build habit.

### Goal representation

```ts
type GoalResponse = {
  id: string;
  habit: {
    id: string;
    name: string;
    type: "build" | "break";
  };
  title: string;
  description: string | null;
  created_at: string;
  updated_at: string;
};
```

The embedded habit summary lets the goal screen display linkage without
requiring a client-side join or a second request.

### `GET /api/goals`

Success: `200 OK` with `GoalResponse[]`, ordered by `updated_at` descending and
then `id` ascending.

The query joins through habits and scopes `habits.user_id` to the authenticated
user.

### `POST /api/goals`

Request:

```ts
type CreateGoalRequest = {
  habit_id: string; // UUID of an owned habit
  title: string; // trimmed result: 1..120 characters
  description?: string | null; // trimmed result: 1..500, blank becomes null
};
```

Example:

```json
{
  "habit_id": "186b3c50-9a9e-4802-b167-bbbd71632d4a",
  "title": "Make meditation automatic",
  "description": "Practice after breakfast every day."
}
```

Success: `201 Created` with `GoalResponse`.

Failure: `404 RESOURCE_NOT_FOUND` when the linked habit is unknown or belongs to
another user.

### `PATCH /api/goals/:goal_id`

Request:

```ts
type UpdateGoalRequest = {
  habit_id?: string;
  title?: string;
  description?: string | null;
};
```

The object must contain at least one property. Field normalization and limits
match goal creation. Blank description becomes `null`; omitting description
preserves the current value.

Success: `200 OK` with the updated `GoalResponse`.

Failures:

- `404 RESOURCE_NOT_FOUND` when the goal is unknown or differently owned; and
- `404 RESOURCE_NOT_FOUND` when a requested replacement habit is unknown or
  differently owned.

### `DELETE /api/goals/:goal_id`

Success: `204 No Content`.

Failure: `404 RESOURCE_NOT_FOUND` when the goal is unknown or differently owned.

## Error contract

Every handled error response uses:

```ts
type ErrorResponse = {
  error: {
    code:
      | "VALIDATION_ERROR"
      | "AUTHENTICATION_REQUIRED"
      | "INVALID_CREDENTIALS"
      | "EMAIL_ALREADY_EXISTS"
      | "RESOURCE_NOT_FOUND"
      | "INVALID_HABIT_TYPE_OPERATION"
      | "DATE_NOT_ELIGIBLE"
      | "RATE_LIMITED"
      | "INTERNAL_ERROR";
    message: string;
    field_errors?: Record<string, string[]>;
  };
};
```

Status mapping:

| Status                      | Codes                                                                       |
| --------------------------- | --------------------------------------------------------------------------- |
| `400 Bad Request`           | `VALIDATION_ERROR`                                                          |
| `401 Unauthorized`          | `AUTHENTICATION_REQUIRED`, `INVALID_CREDENTIALS`                            |
| `404 Not Found`             | `RESOURCE_NOT_FOUND`                                                        |
| `409 Conflict`              | `EMAIL_ALREADY_EXISTS`, `INVALID_HABIT_TYPE_OPERATION`, `DATE_NOT_ELIGIBLE` |
| `429 Too Many Requests`     | `RATE_LIMITED`                                                              |
| `500 Internal Server Error` | `INTERNAL_ERROR`                                                            |

Example validation failure:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Check the highlighted fields.",
    "field_errors": {
      "email": ["Enter a valid email address."],
      "password": ["Use at least 8 characters."]
    }
  }
}
```

Unexpected database and programming errors are logged with internal context and
returned as the generic `INTERNAL_ERROR` response. MySQL messages, SQL text,
stack traces, and constraint names are never returned to the browser.

## Ownership and repository behavior

Repository methods that operate on owned data require `userId` as an explicit
argument. Before executing SQL, the repository converts every validated UUID
argument to a 16-byte buffer. UUID select projections use
`LOWER(BIN_TO_UUID(column))` so MySQL returns canonical lowercase strings and no
casing-only row mapper is needed.

Keep the two conversion functions in one database utility, for example
`database/binary-uuid.ts`. They must:

- accept only a canonical UUID already validated at the transport or application
  boundary;
- remove hyphens and decode exactly 32 hexadecimal digits into 16 bytes;
- reject any buffer whose length is not exactly 16 bytes when a fixture, test,
  or query intentionally decodes a raw binary UUID;
- encode bytes to 32 lowercase hexadecimal digits and restore the canonical
  `8-4-4-4-12` hyphen grouping; and
- round-trip UUID values without applying byte or time-field swapping.

Ordinary application predicates bind these buffers directly rather than
wrapping indexed columns in conversion functions. `BIN_TO_UUID()` is used only
in the selected projection, not the predicate, so indexed lookups remain intact.
The binary conversion utility remains independently round-trip tested for input
binding, fixtures, and other database-boundary uses.

Use ownership-scoped SQL patterns:

```sql
SELECT ...
FROM habits
WHERE id = ? AND user_id = ?
```

Child resources join through habits:

```sql
SELECT goals.*
FROM goals
INNER JOIN habits ON habits.id = goals.habit_id
WHERE goals.id = ? AND habits.user_id = ?
```

Rules:

- Never load a resource by ID alone in an authenticated use case and assume a
  later frontend check provides authorization.
- Return the same typed not-found error for an unknown and differently owned
  identifier.
- Parameterize every value; never interpolate an identifier, date, sort value,
  email, or search value into SQL.
- Keep the small set of sort expressions fixed in repository code rather than
  accepting raw client sort names.
- Map MySQL rows, including binary UUID values, to explicit application values;
  do not return driver row types or buffers from repositories.

## Transactions, idempotency, and concurrency

### Authentication

User registration is one insert protected by the unique email index. Translate
only the known email-constraint violation into `EMAIL_ALREADY_EXISTS`; do not
treat every duplicate-key error as an email conflict.

### Completion mutation

Run a completion mutation on one acquired connection:

1. begin a transaction;
2. select the owned habit `FOR UPDATE`;
3. verify build type and date eligibility;
4. for `PUT`, insert with duplicate-safe ensure-present semantics;
5. for `DELETE`, delete the composite key if present;
6. read the completion dates needed to calculate the returned current-week
   state and current streak;
7. commit; and
8. return the mapped response.

The composite primary key is the final concurrency guarantee. A duplicate-safe
insert must not overwrite `created_at` on a repeated request.

### Relapse mutation

Use the same owned-habit lock pattern:

1. begin a transaction;
2. select the owned habit `FOR UPDATE`;
3. verify break type;
4. insert today's relapse with duplicate-safe ensure-present semantics;
5. select the latest relapse;
6. commit; and
7. return recalculated state.

### Goal mutation

- Creation verifies the linked habit with an ownership-scoped lookup before the
  insert.
- Updating linkage verifies both the owned goal and replacement owned habit in
  one transaction.
- Updating fields without changing the linked habit can use one
  ownership-scoped update followed by a mapped read.
- Deletion uses one ownership-scoped delete through the habit relationship.

### Habit deletion

Delete the habit with both `id` and `user_id` in the predicate. Foreign-key
cascades remove children atomically; application code does not manually delete
each child table.

  definitions, or domain services to the contracts package.

## Read-model query strategy

`GET /habits` must avoid per-card database queries. A suitable implementation
uses a small bounded set of parameterized queries:

1. fetch all owned habits in stable order;
2. fetch selected-week completions for the returned build habit IDs;
3. fetch the completion history necessary for current streaks; and
4. fetch the latest relapse per returned break habit.

Because a streak may span an arbitrary history, the first implementation may
retrieve ordered completion dates for the user's build habits and group them in
the application layer. If data volume later demonstrates a problem, introduce a
bounded gap query or SQL window strategy with equivalent domain tests. Do not
persist a counter merely to optimize before measuring.

`GET /goals` performs one join to habits and returns the embedded habit summary
from the same query.

## Chosen trade-offs

### Binary UUID storage instead of textual UUID columns

MySQL stores entity UUIDs in `BINARY(16)` rather than a 36-byte hyphenated text
column. This reduces primary-key, foreign-key, and index width and avoids
character-set or collation semantics for identifiers. The public API, domain
code, logs, and tests still use canonical UUID strings.

The cost is explicit conversion during repository parameter binding and select
projection. Centralizing and testing that conversion is preferable to repeating
36-byte keys across InnoDB indexes. UUIDv4 bytes retain their original order;
the MySQL version-1 time-field swap flag is not used.

### Event rows instead of stored counters

Completions and relapses are source events. Streaks and weekly results are
derived so backfills, corrections, and retries cannot leave counters out of
sync.

### Composite tracking keys instead of event UUIDs

The natural habit/date identity directly enforces one event per calendar day
and makes idempotent mutation behavior obvious.

### Raw SQL instead of an ORM

The selected architecture uses a small `mysql2/promise` repository layer. The
schema and ownership joins are simple enough to remain explicit, and real-MySQL
integration tests protect mappings and constraints.

### One access token instead of refresh sessions

An HTTP-only same-site cookie satisfies the coding-test authentication scope.
Refresh rotation, revocation, device sessions, and password reset would add a
separate security subsystem without supporting a required journey.

### Server-derived dates instead of browser trust

The stored user timezone and server clock provide consistent ownership of
"today." Browser dates remain display hints and cannot create future or
out-of-policy tracking events.

### Current-week correction instead of unrestricted backfill

Users can fix recent mistakes without adding a full calendar-editing product.
Historical weekly reads remain deterministic, while historical mutations are
outside the MVP.
